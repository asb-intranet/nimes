# V121 — Notifications Web Push
1. Sauvegarder la base, tester sur copie, exécuter supabase/schema-v121.sql après V120.
2. Générer localement les clés avec Node.js : `node generate-push-keys.cjs` (une seule fois). Ne pas partager les valeurs privées. Ajouter dans Vercel Production les trois variables affichées et ASB_VAPID_SUBJECT = mailto:adresse-administrateur-valide. La clé publique est publique, les deux autres sont Secret. Conserver les clés V119.
3. Publier et redéployer V121. Dans Supabase > Database > Webhooks, créer un webhook sur public.asb_push_events, événement INSERT uniquement, méthode POST, URL https://VOTRE-DOMAINE/api/push, header x-asb-push-secret = valeur ASB_PUSH_WEBHOOK_SECRET, Content-Type application/json, timeout 10000 ms si disponible. Ne pas exposer ce secret. Sans webhook aucun envoi automatique.
4. Sur chaque appareil, ouvrir ASB, rubrique Notifications, choisir les événements et Activer / enregistrer. iOS 16.4+ : ajouter à l'écran d'accueil puis ouvrir depuis l'icône. Tester deux comptes distincts, appareil verrouillé, création/modification de demande, statut, message individuel, planning et prestation. Déconnexion désabonne l'appareil.
5. Les demandes et prestations terminées notifient les comptes admin (pas de rôle magasinier distinct dans V120). Les autres événements ciblent les salariés actifs concernés. Contenu générique sur écran verrouillé. Les préférences sont enregistrées côté serveur par appareil, mais le formulaire réaffiche les valeurs par défaut à l'ouverture. Les échecs restent dans la table asb_push_events ; pas de relance automatique ni de garantie de livraison. Surveiller les logs webhook et Vercel. Les modifications multiples du planning peuvent produire plusieurs notifications. Aucun cache hors ligne ajouté. Le transport Web Push utilise les primitives crypto Node, sans nouvelle dépendance ; test réel des services push indispensable. Pas de compilation complète ici.
